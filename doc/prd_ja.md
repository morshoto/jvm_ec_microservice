# PRD: マイクロサービスアーキテクチャを採用した EC サイトバックエンドの開発

## 1. プロジェクト概要

**プロジェクト名:**  
マイクロサービス EC バックエンド

**概要:**  
本プロジェクトは、複数の独立したサービスが協調しながら機能するマイクロサービスアーキテクチャを用い、EC サイトのバックエンドを実装することを目的とします。サービスディスカバリ、負荷分散、API Gateway、障害耐性（リトライ・サーキットブレーカー）、分散ロギング・モニタリングなど、スケーラブルで高可用性を実現するための実践的な技術を習得しながら、実際のプロダクトとして機能するシステムを構築します。

---

## 2. ビジネス背景と目的

**背景:**

-   急速な EC 市場の成長に伴い、システムの可用性・スケーラビリティが求められる。
-   大規模なトラフィックや急激なアクセス増加に対応するため、モノリシックアーキテクチャではなく、疎結合のマイクロサービスアーキテクチャが有効。
-   チームの開発効率向上やサービス単位での独立したデプロイ・スケールが実現できる。

**目的:**

-   マイクロサービスの基本設計思想および主要ツール（Spring Cloud、Netflix OSS）の習得
-   可用性、拡張性、保守性が高いシステム設計の経験獲得
-   開発したシステムをポートフォリオとして、オープンソースコミュニティへの貢献や就職・転職活動での実績とする

---

## 3. プロジェクト範囲

**対象機能:**

-   **ユーザー管理サービス:** ユーザー登録、認証、プロフィール管理
-   **商品管理サービス:** 商品登録、カタログ表示、検索機能
-   **在庫管理サービス:** 商品の在庫状況の管理と更新
-   **注文管理サービス:** 注文受付、注文処理、キャンセル機能
-   **決済サービス:** 決済処理のインターフェースと外部決済ゲートウェイとの連携
-   **配送管理サービス:** 発送ステータスの更新、配送状況のトラッキング

**インフラ・共通コンポーネント:**

-   **API Gateway (Zuul):** 各サービスへのルーティング、認証、リクエストの集約
-   **サービスディスカバリ (Eureka):** サービス登録と探索、動的なエンドポイント管理
-   **クライアントサイド負荷分散 (Ribbon):** 各サービスの呼び出し時に負荷分散処理
-   **サーキットブレーカー (Hystrix):** 障害時のフェールセーフ対応、フォールバック処理
-   **分散ロギング・モニタリング:** ログ集約（ELK スタックなど）、メトリクス監視（Prometheus、Grafana など）

**除外範囲:**

-   フロントエンド（ユーザーインターフェース）の実装は含まず、API レベルの開発に集中
-   外部パートナー連携の実装はモックやシミュレーションで対応

---

## 4. ターゲットユーザーとステークホルダー

**ターゲットユーザー:**

-   社内開発チーム（マイクロサービスの実装・運用、DevOps エンジニアリングの実践）
-   オープンソースコミュニティのメンバー（実装例として学習・拡張可能なプロジェクトとして）
-   技術面接や転職活動での実績としてアピール可能なエンジニア

**ステークホルダー:**

-   プロダクトオーナー／プロジェクトマネージャー: プロジェクトの方向性・進捗管理
-   開発チーム（フロントエンドは別チーム）: 各マイクロサービスの設計・実装
-   DevOps エンジニア: CI/CD パイプラインの設定、運用監視システムの構築
-   QA エンジニア: 各サービスのテスト設計、統合テストの実施

## 5. 主要機能詳細

### 5.1 ユーザー管理サービス

-   **機能:**
    -   ユーザー登録／ログイン（JWT 等による認証トークン発行）
    -   プロフィール更新、パスワードリセット
-   **API:**
    -   POST /users/register, POST /users/login, GET /users/{id}

### 5.2 商品管理サービス

-   **機能:**
    -   商品の登録、更新、削除
    -   商品一覧や詳細表示、カテゴリ別検索
-   **API:**
    -   CRUD 操作のエンドポイント、検索 API（GET /products, GET /products/{id}）

### 5.3 在庫管理サービス

-   **機能:**
    -   商品の在庫レベル管理
    -   在庫不足時のアラート、在庫更新イベントの発行
-   **API:**
    -   在庫確認（GET /inventory/{productId}）、在庫更新（POST /inventory/update）

### 5.4 注文管理サービス

-   **機能:**
    -   注文受付、注文詳細の管理
    -   注文状態（新規、処理中、配送中、キャンセル）の更新
-   **API:**
    -   POST /orders、GET /orders/{id}、PUT /orders/{id}/status

### 5.5 決済サービス

-   **機能:**
    -   決済リクエストの受け付けと処理
    -   外部決済 API（例: PayPal, Stripe など）の連携用インターフェース
    -   決済ステータスの更新と確認
-   **API:**
    -   POST /payments、GET /payments/{orderId}

### 5.6 配送管理サービス

-   **機能:**
    -   発送処理、配送ステータス更新
    -   配送業者との連携（シミュレーションまたはモックデータ使用）
-   **API:**
    -   POST /shipping、GET /shipping/{orderId}

### 5.7 共通基盤（API Gateway・サービスディスカバリ等）

-   **API Gateway (Zuul) の役割:**

    -   すべてのクライアントリクエストの統一エントリポイント
    -   認証フィルター、ルーティング、リクエストロギングの実装

-   **サービスディスカバリ (Eureka) の役割:**

    -   各サービスの動的登録、クライアントによるサービス検索の実装

-   **耐障害性:**
    -   Hystrix によるサーキットブレーカー、フォールバック処理の実装
    -   Ribbon によるクライアントサイドロードバランシング

---

## 6. 非機能要件

-   **スケーラビリティ:**

    -   各サービスは独立してスケールできる設計
    -   API Gateway が大量のリクエストを効率的にルーティングする

-   **高可用性:**

    -   サービスディスカバリによる冗長化
    -   サーキットブレーカーにより障害箇所の早期検知とフォールバック

-   **パフォーマンス:**

    -   各 API のレスポンスタイムを 200ms 以下を目標
    -   キャッシュやロードバランサーを適宜配置

-   **セキュリティ:**

    -   認証・認可の実装（JWT、OAuth2 等）
    -   API Gateway におけるリクエストフィルタリングと攻撃対策

-   **監視・ロギング:**
    -   分散トレーシング（Spring Cloud Sleuth、Zipkin 等）
    -   ログ集約システムの整備（例: ELK スタック、Fluentd）

---

## 7. 技術スタックとアーキテクチャ設計

**言語・フレームワーク:**

-   Java（JDK 11 以降）／Kotlin（オプション）
-   Spring Boot / Spring Cloud
-   Netflix OSS（Eureka, Zuul, Ribbon, Hystrix）

**インフラ:**

-   コンテナ化（Docker）を前提とした各サービスのパッケージング
-   オーケストレーション（Kubernetes または Docker Compose）
-   CI/CD パイプライン（GitHub Actions、Jenkins 等）

**アーキテクチャ概要:**

-   各サービスは独立した Spring Boot アプリケーションとして実装
-   API Gateway（Zuul）がフロントエンドからのリクエストを受け、認証・ルーティングを実施
-   Eureka サーバーにより、各サービスは自身のエンドポイントを登録し、クライアント側は Ribbon によるロードバランシングでサービスを呼び出す
-   Hystrix による障害検知とフォールバック機能により、システム全体の信頼性を確保

## 8. ユーザーストーリー

-   **ユーザーとして:**  
    「商品一覧をブラウズし、気に入った商品をカートに入れ、注文を確定できること」

    -   カタログサービスで商品情報を取得
    -   注文サービスで注文情報を登録し、決済サービス経由で決済が完了する

-   **管理者として:**  
    「商品の追加・在庫数の調整、注文のキャンセルや変更が迅速に行えること」

    -   管理者用ポータル（API 経由で実装）を利用して、各サービスの管理操作を実施

-   **開発者として:**  
    「個々のサービスが疎結合であるため、新機能の追加やバグ修正が他に影響を与えず実施できること」
    -   各マイクロサービスのテスト、統合テストを通じて開発・デプロイをスムーズに行える

---

## 9. 受入基準（Acceptance Criteria）

-   各サービスが個別にビルド・デプロイでき、API Gateway 経由で統合されたエンドポイントにアクセス可能なこと
-   サービスディスカバリを用いて、各サービスが自動的に登録・発見されること
-   Hystrix によるサーキットブレーカーが適切に機能し、特定サービス停止時にフォールバックが実行されるシナリオをテストで検証
-   スケールアウトテストにおいて、リクエストレスポンスが仕様内（例: 200ms 以下）に収まること
-   セキュリティテストにより、認証・認可処理が期待通りに動作すること

---

## 10. タイムラインとマイルストーン

1. **調査・設計フェーズ（2〜3 週間）**

    - マイクロサービス全体のアーキテクチャ設計・技術選定
    - 各サービスの仕様策定とインターフェース設計

2. **プロトタイプ開発フェーズ（4〜6 週間）**

    - API Gateway、ユーザー・商品・注文サービスの実装
    - Eureka サーバーと初期のサービス登録機構の構築

3. **機能拡張・統合テストフェーズ（4 週間）**

    - 在庫、決済、配送サービスの実装
    - サーキットブレーカー、負荷分散、分散トレーシングの統合

4. **最終テスト・パフォーマンス最適化フェーズ（2〜3 週間）**

    - システム全体の負荷テスト、セキュリティテスト、エンド・ツー・エンドテスト
    - CI/CD パイプラインの整備、デプロイメント自動化の確認

5. **リリース準備・ドキュメント整備（1〜2 週間）**
    - ユーザードキュメント、API リファレンス、運用マニュアルの作成
    - 最終レビューとフィードバック反映

## 11. リスクと対策

-   **通信遅延や障害:**
    -   対策: Hystrix でのサーキットブレーカー実装、リトライ・タイムアウトの設定
-   **データ一貫性の担保:**
    -   対策: 分散トランザクションの回避（イベント駆動の eventual consistency を採用）
-   **運用監視の不足:**
    -   対策: ログ集約システム・メトリクス監視ツール（Prometheus、Grafana 等）の早期導入
-   **各サービス間のインターフェース変更:**
    -   対策: API 契約（API Contract）の明文化、バージョニングの実施、統合テストの自動化
